### F1 — Catch-all deployment rewrite hides real missing resources

- **Observed:** unknown path, `/assets`, `/robots.txt`, and `/sitemap.xml` all returned `200 text/html` with `ERL AssetHub · Workspace access`. Local Vite preview reproduces the shell fallback. Live unknown-path response is saved as [production-unknown.html](evidence/seo-2026-10-25/production-unknown.html); crawler responses are [production-robots.html](evidence/seo-2026-10-25/production-robots.html) and [production-sitemap.html](evidence/seo-2026-10-25/production-sitemap.html).
- **Expected:** unknown document/resource paths return real `404` responses. If provided, robots must be plain-text rules and sitemap must be valid XML. It is also acceptable to omit these optional resources and return `404` rather than homepage HTML.
- **Impact:** arbitrary paths create duplicate access-page URLs and possible soft-404 classification; crawler-resource requests receive the wrong document. Google classification itself was not measured. This is not a claim that a missing sitemap prevents indexing.
- **Confirmed cause:** `vercel.json:13` rewrites all non-API paths to `/index.html`. App navigation reads `location.hash` in `frontend/src/App.jsx:56`, so arbitrary pathname fallback is unnecessary for the existing private hash routes.
- **Exact fix:** narrow/remove the second rewrite in `vercel.json:13`, preserving `/api` routing, root access, real static assets, and `/?invite=...`. Let unknown paths return platform `404`; an optional `frontend/public/404.html` can provide a useful error page. If a robots file is desired, add `frontend/public/robots.txt`. Only add `frontend/public/sitemap.xml` if there are intended indexable URLs; list root or future public pages only, never fragments, invitation tokens, APIs, or tenant records. Use absolute URLs from trusted configuration and truthful dates.
- **Verification:** deploy through the normal release process when authorized, then GET root, invitation query, a real JS/CSS/favicon asset, `/api/health`, and `/#dashboard`; these must continue working. GET two random unknown paths and a missing asset and confirm `404`. Fetch robots/sitemap and confirm either valid content and content type or honest `404`. Vite preview fallback alone cannot verify Vercel edge routing.

### F2 — Invitation URLs do not declare `noindex`

- **Observed:** `/?invite=seo-audit-invalid-token` returns `200` with no `X-Robots-Tag` or robots meta before or after rendering. The DOM changes to “Join your team”. Real one-use invitation URLs are generated in `backend/src/controllers/workspaceController.js:859`.
- **Expected:** account invitation workflows should be excluded from search indexing. A crawlable `noindex` response communicates this without altering invitation validity or authentication.
- **Impact:** invitation URLs have no explicit indexing exclusion if a crawler discovers them. No evidence establishes that any real invitation is indexed or that tenant data is exposed.
- **Confirmed cause:** `frontend/index.html:7` has only a description; `frontend/src/App.jsx:398` detects invite queries for display/title but does not own robots metadata. `vercel.json` has no response-header rules.
- **Exact fix:** prefer a query-matched `X-Robots-Tag: noindex` response rule for the root `invite` parameter in `vercel.json`, verified against the hosting platform's query-matcher behavior. Preserve `location.search` and token handling. If the entire demo app should be excluded, use a shared initial `noindex` policy instead and keep discovery on a public case study/landing page. Never use an invitation URL as a canonical or social URL. Do not rely on `robots.txt` disallow or canonical alone to remove invitations from search.
- **Verification:** compare root, a tracking-only query, and a synthetic invitation URL in initial HTTP headers and rendered DOM. Confirm the invitation has `noindex`; confirm root matches the chosen visibility policy. Verify the rule on the deployed environment, including empty/combined query variants. No real token is needed for this test.

Hash fragments are not separate HTTP pages. The server cannot selectively emit a different header for `/#assets` and `/` based on the fragment. Keep private records behind API authentication rather than trying to publish per-asset SEO metadata or sitemap entries.

### F3 — Shared page has no explicit social preview

- **Observed:** no `og:*` or `twitter:card` metadata in initial or rendered HTML; no public preview-image URL. The only image-like public asset is the SVG favicon. `.github/media/social-preview.png` exists in the repository, but it is outside Vite's public output and was not validated as a suitable page preview asset.
- **Expected:** sharing the public demo/access URL should have a stable, accurate title, description, and accessible absolute preview-image URL. Platforms may still generate fallbacks today; their actual previews were not tested.
- **Impact:** link-preview quality is uncontrolled. These tags are not direct ranking requirements.
- **Confirmed cause:** `frontend/index.html:7–24` contains the shared title/description but no social tags. `frontend/public/` has only the favicon.
- **Exact fix:** add a single Open Graph metadata set plus an appropriate Twitter/X card in `frontend/index.html`, using the existing truthful product description and trusted production origin. Add a suitable image under `frontend/public/`, inspect its actual dimensions/content before declaring image dimensions, and verify the built asset is served. Reuse the existing repository image only after inspection. Keep invite tokens and tenant information out of metadata. Do not introduce a second head-management package for static tags.
- **Verification:** inspect built and deployed initial HTML for one effective tag set; fetch the absolute image URL and confirm a supported image content type, successful response, and correct dimensions. Verify real platform previews separately if access is available.

### F4 — Public discovery depends on client rendering

- **Observed:** initial live/local HTML contains `<div id="root"></div>` with no headings or page copy. Chromium subsequently renders `Every asset. In good hands.`, `Welcome back`, and the demo disclosure with no page JavaScript exceptions. This is confirmed client rendering, not proof that Google cannot index the page.
- **Expected:** if root is intended as a public product/search landing page, meaningful product copy and navigation should be available in the initial response. A deliberately unindexed login/demo app does not need an SSR migration for SEO.
- **Impact:** public content discovery depends on crawler JavaScript execution. Social crawlers commonly depend on initial metadata. The private workspace is not expected to be crawlable.
- **Confirmed cause:** `frontend/index.html:27` supplies an empty root; `frontend/src/main.jsx:8` uses React `createRoot`; content lives in `frontend/src/pages/Access.jsx:137`. There is no server/static rendering step in `frontend/vite.config.js`.
- **Exact fix:** first document whether the demo root is a search destination in `docs/overhaul/deployment.md`. For public discovery, prefer a small Vite-compatible static/prerendered public page with accurate visible content and a real link into the existing application, or make the existing public case study the discoverable destination. Preserve hash navigation and private access. Any prerendering must avoid session-dependent or invitation content. No framework migration is justified by this audit alone.
- **Verification:** after a rendering change, fetch the initial public response and confirm meaningful copy and links without JavaScript, then confirm normal React loading and private navigation. If the app remains intentionally unindexed, mark this finding not applicable and verify its exclusion policy instead.

### F5 — Tracking duplicates lack a canonical preference

- **Observed:** `/` and `/?utm_source=seo-audit` return the same access page and metadata; neither has a canonical or canonical HTTP `Link` header. No redirect consolidates the tracking variant.
- **Expected:** if root is indexable, a single absolute preferred URL can identify `https://erlassethub.vercel.app/` as the public copy.
- **Impact:** search engines receive less explicit guidance about identical query aliases. Missing self-canonical alone is not an indexing failure or evidence of a duplicate-content penalty.
- **Confirmed cause:** there is no canonical owner in `frontend/index.html`; Vercel serves the root document for query variants.
- **Exact fix:** add one trusted-origin root canonical in the shared initial head at `frontend/index.html:11` if indexing root is intentional. Keep production origin configurable if environments require it. Do not derive it from arbitrary request `Host`, include tracking/invitation parameters, or treat canonical as the invitation exclusion fix. Preserve meaningful invitation query parameters in application navigation.
- **Verification:** check initial HTML of root and tracking variant for exactly one absolute preferred URL. Separately confirm invitation `noindex`, no competing HTTP canonical, and no accidental canonicalization to a preview or unrelated origin. If the application is intentionally unindexed, this is low-value optional work.

## Correct behavior and non-findings

- Initial title is descriptive: `ERL AssetHub · Workspace access` (31 characters). Existing description is accurate for login/demo access. Length heuristics alone do not justify rewriting it.
- `lang="en"` matches the English interface. Viewport supports normal mobile sizing and does not disable zoom. Sampled access DOM has one H1 and a reasonable H1/H2/H3 hierarchy. No locale-equivalent routes were found, so hreflang is not required.
- No HTML `<img>` elements appear on the sampled access page. Icons are not automatically missing-alt defects. The source for the private QR image supplies descriptive alt text at `frontend/src/pages/AssetsPage.jsx:856`; that private image was not rendered in this audit.
- The anonymous access-page home link is a real `<a href="/">` with an accessible name. Buttons switching forms and private app pages do not need to become crawler links. No public listing/article/product collection was found.
- Missing JSON-LD is not an indexing blocker. Optional accurate `WebSite`/`SoftwareApplication` markup belongs only on a suitable public page; do not invent pricing, reviews, ratings, or rich-result eligibility. No JSON-LD changes or validation were performed.
- Sampled private API requests return real `401` JSON. `backend/src/server.js:44` gates workspace routes with authentication and active membership. This bounded anonymous check is not a full tenant isolation/security audit.
- Missing-record checks and API `404` mapping exist in source (`backend/src/controllers/workspaceController.js:27`, `backend/src/server.js:123`); authenticated missing-record behavior remains unverified.
- `backend/src/lib/api.js:128` derives public origin from trusted deployment settings, validates protocol/credentials, and does not trust the incoming request host. Reuse that policy for future server-generated URLs.
- Prisma models represent private operational records, not published CMS content. No SEO fields, migrations, draft states, or backfills are indicated.
- Sampled API responses have `Cache-Control: public, max-age=0, must-revalidate` and Vercel `MISS`. Optional explicit `private, no-store` for session/tenant responses and API `X-Robots-Tag: noindex` would clarify intent in `backend/src/server.js`; no authenticated caching leak or API indexing problem was established. Keep this separate from verified SEO findings.
- Missing sitemap alone is not a blocker for a one-page demo/access site. A sitemap must never enumerate private asset hashes or invitations.
